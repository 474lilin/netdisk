# 06 - 风险提示（MinIO 集群部署注意事项 / 备份策略 / 企业交付注意点）

## 1. MinIO 集群部署注意事项

1. **节点数 ≥ 4，且固定不变**：MinIO 纠删码（Erasure Coding）的冗余策略在首次启动时确定；
   集群一旦建立，**严禁减少节点/磁盘**，否则数据不可恢复。规划容量时留足 1.5-2 倍余量。
2. **每个节点使用独立物理磁盘**：不要用 RAID 0 / RAID 5 把多盘合成一块再交给 MinIO
   （MinIO 自带纠删码，RAID 反而降低可靠性）；建议每节点 2-4 块盘分别挂载为独立数据卷。
3. **时钟同步（NTP）必须开启**：节点间时间偏差过大（>15 分钟）会导致签名/一致性异常。
4. **网络要求**：节点间延迟 < 5ms 为宜（同机房）；跨地域部署会显著降低性能。
5. **单机默认（单盘）无冗余**：单盘故障即丢数据，每日备份是唯一防线；单机 4 盘纠删码
   模式（需 4 块独立物理盘）可容忍 2 盘故障，但服务器整体宕机仍需备份恢复。
6. **在线扩容只能加节点**（如 4 → 6），且旧数据重平衡为异步，期间容量占用翻倍预期；
   不支持缩容。生产建议使用 `mc admin info` 定期巡检。
7. **版本控制与生命周期**：本系统依赖桶版本控制实现文件版本/回滚；`deploy/minio-init/init.sh`
   已配置非当前版本 30 天自动清理，如需更长历史版本保留期请调整生命周期规则（注意存储成本）。
8. **Console 安全**：MinIO Web 管理台（9001）具有 root 权限，生产务必仅内网访问，
   或移除端口映射（`docker compose` 中注释掉 9001 端口）。

## 2. 备份策略（红线）

1. **元数据 + 对象必须成对备份**：PG 丢 = 文件清单丢失；MinIO 丢 = 内容丢失。
   使用项目 `deploy/scripts/backup.sh`（pg_dump + mc mirror），每日执行。
2. **备份异地存放**：与生产机房隔离（另一机房/脱机介质），防止机房级故障。
3. **定期演练恢复**：每季度在测试机完整恢复一次，验证备份可用性（很多企业"有备份没恢复"）。
4. **大版本升级前必须备份**：升级 MinIO / PostgreSQL / 业务代码前先跑一次备份。
5. **回收站清空不可恢复**：用户"彻底删除"与超期自动清理会真正删除对象（含版本），
   前端已二次确认；如需更严格保护，可为桶开启对象锁定（Object Lock，需在 minio-init 时配置）。

## 3. 企业交付注意点

1. **密钥管理**：.env 是全部凭据的唯一来源，务必：
   - 生成强随机值（`openssl rand -base64 48`），禁止复用默认值；
   - .env 禁止提交到 Git（已加入 .gitignore）；
   - 交接时明确保管人，离职轮换。
2. **内网安全基线**：
   - 前端仅对内网开放；如必须公网访问，务必前置 HTTPS + 强口令 + 访问控制；
   - MinIO 签名 URL 有效期默认 1 小时（PRESIGN_EXPIRY），如安全要求高可缩短；
   - 分享链接仅内网可达；告知员工禁止将链接/文件外发（可用审计日志抽查 share_download 记录）。
3. **合规审计**：全部文件/权限/分享操作已记录到 `audit_logs`（审计日志可导出）；
   建议定期导出归档（默认保留 365 天），满足企业合规要求。
4. **账号体系**：默认本地账号密码登录；对接企业 AD/LDAP 时按
   `server/src/ldap/provider.ts` 中的 TODO 实现（接口已预留，配置项 LDAP_* 已就绪）。
5. **容量规划**：去重秒传不限文件大小（无 DEDUP_MAX_SIZE 上限）；首次去重时池哈希在线校验仅对
   ≤1GB（DEDUP_INLINE_MAX 可调）的文件生效，超过 1GB 且后台校验未完成时会回退为正常上传（同内容
   文件暂时重复存储，后台校验完成后后续再传即秒传）；配额三级管控（用户>部门>企业）生效级别为"最严的一级"。
6. **故障恢复预期**：
   - 单机单盘：单盘故障 = 数据丢失，走备份恢复（默认模式，每日备份是唯一防线）；
   - 4 盘纠删码模式：单盘故障自动恢复、双盘故障只读不丢，尽快换盘；
   - 多盘/整机故障：走备份恢复（RTO 取决于数据量，建议演练）。
7. **运维交接文档**：交付时提供本文档 + 03-运维手册 + 04-备份与恢复，
   并培训运维人员掌握 `docker compose` 基本操作与健康检查方法。

## 4. 已知限制（诚实声明）

| 限制 | 说明 | 规避 |
|---|---|---|
| 旧版 .doc / ppt 不能在线预览 | 离线环境无 Office 服务 | 下载后本地查看；可后续接入内网 OnlyOffice 并自行扩展 |
| 目录分享不支持整包下载 | 不引入额外 zip 依赖 | 目录分享支持逐文件/逐子目录浏览下载 |
| 超大文件秒传需先本地哈希 | 去重需先本地 BLAKE3 分段并行哈希（B3SEG，8MB 分片多线程，耗时与文件大小成正比，近似本地磁盘读速） | 上传队列会显示"计算哈希"阶段；大文件建议在本地机器操作 |
| 首个重复可能等待池校验 | 大文件池对象哈希为后台校验；首个重复若恰逢校验未完成会等待其完成（一次性） | 之后永久免验，秒传纯元数据 |
| 秒传文件无独立版本历史 | 秒传文件共享池对象，不支持版本回滚 | 覆盖上传会脱离共享转为独立对象，之后恢复版本能力 |
| 登录限流为单实例内存 | 多后端实例时计数不共享 | 规模小可接受；严格场景可升级 Redis |
| 同名文件上传 = 新版本 | 不会自动改名为"xxx(1)" | 符合版本管理语义，可回滚 |
| 单节点多盘纠删码性能损失 | 单机多"盘"若为同一物理盘/同一挂载，纠删码仅带来 I/O 放大而无冗余收益（实测 MinIO 读写 ~20-100MB/s，4 核 Docker VM） | 单节点建议单数据目录（无纠删码）；数据盘优先命名卷/SSD；纠删码仅在多块真实独立物理盘上才有意义（见 03-运维手册 存储调优） |
| 首遍哈希受存储路径限制 | B3SEG 段缓存（内存）只加速重复校验；首次哈希仍需从 MinIO 读取（~100MB/s） | 提高 MinIO 存储性能（SSD/命名卷）可同时加速首遍哈希与上传 |
